## Verdict

The current prototype now follows the v2 agent-style product track: arbitrary topic onboarding, learner profile, research brief, planner draft, curriculum validator, dynamic feed/lesson/comments, and shadow draft. Web3 remains as a sample fallback curriculum, not the product boundary.

The main architecture risk is no longer "Web3-only implementation"; it is letting convenience fixes bypass the validator/engine boundary. Future work must keep LLM output as draft/expression data while local code owns stable IDs, path order, progress, mastery, unlock state, and approved/public shadow state.

## Prototype Gaps That Are Not Drift

These are known incompletions, but they do not mean the project has changed direction:

1. Planner quality is prototype-grade. The fallback planner has topic templates plus a generic path, and the structural eval catches state-boundary leaks, research mismatch, and sample leakage. It is not yet a semantic quality or factuality eval.
2. Research quality is still lightweight. The proxy now dedupes, ranks by topic relevance, filters low-signal results, and exposes `qualityScore` / `qualitySignals` / `factReviewStatus`, but these are planning-only retrieval signals, not a factual review or citation-grade source audit.
3. Comment threads are still prototype-grade, but no longer purely flat. The app now exposes `全部` / `赞成` / `反对` / `补充` / `挑刺`, renders lightweight nested replies with optional quotes, and lets learners switch top-level comment ordering between `热度`, `新回复`, and `相关`. It rejects placeholder author names, prevents reply self-dialogue, derives topic/concept-specific fallback personas for missing or placeholder community authors, and real LLM E2E fails if the visible thread lacks at least two replies, contains any repaired reply, contains self-replies, lacks enough learning-signal variety, has mostly stance-only top-level comments, or has 3+ replies without covering `追问` / `反驳` / `补充`. The generation engine retries repaired-reply output, low relation-coverage output, and low top-level-comment learning-signal output before accepting it as `Research + LLM`. The E2E summary records `communityQuality.score` and signals for stance coverage, reply count/relation kinds, sort modes, author diversity, self-reply count, context use, repair filler, off-domain copy, learning-signal kinds, and low-learning-value visible comments across visible comments/replies plus generated-bundle author role/handle/body/reply source. Production hot/new/relevance ranking still needs richer timestamp and personalization signals.
4. Boss checks and longer-term mastery loops are not implemented.
5. The real LLM E2E path supports mobile, laptop, and desktop viewports through the Chrome CDP harness; release verification should still sample more than one scenario across those viewports.
6. Computer Use desktop verification is still blocked locally. `computer-use/list_apps` and `computer-use/get_app_state("Google Chrome")` timed out after 120 seconds, and a later `computer-use/list_apps` retry on 2026-06-11 also timed out after 120 seconds, so current runtime evidence is Chrome CDP E2E rather than macOS desktop interaction. These gaps are product depth and verification gaps, not evidence of a hardcoded-state-machine drift.

## Real Drift Risks To Fix

1. Validator bypass.

   Risk: future agents may let planner or generator output directly mutate stable state.

   Required guard: all generated curriculum drafts must pass through `validateCurriculumDraft`; all generated feed/lesson/shadow output must pass through `parseGeneratedPayload` / generation engine fallback.

2. Silent fallback masking.

   Risk: the app could look functional while using fallback content too often.

   Required guard: keep source labels visible and run real LLM E2E against non-Web3 topics.

3. Community flattening.

   Risk: comments become generic agreement or entertainment instead of learning-oriented disagreement.

   Required guard: keep all visible stance tabs populated, require useful stance diversity, require visible nested replies from different personas, reject placeholder community authors, fail E2E on repair-filler-heavy threads using `FeedCommentReply.source` when present, fail E2E on nonzero `selfReplyCount`, and keep safety checks against personal/group attacks.

4. Web3 fallback leakage.

   Risk: fallback sample authors or terminology can appear in generated non-Web3 paths.

   Required guard: non-Web3 tests must assert no Web3/Gas/wallet leakage.

5. Product spec mentions weekly Boss checks, but the prototype does not implement them.

   Recommended next action: include Boss checks in the next generalized curriculum milestone, not in quick bugfixes.

## Do Not Change Direction

- Do not turn KnowFeed into a fixed Web3 course app.
- Do not make fallback the normal product path.
- Do not let LLM output directly become permanent concept IDs, lesson IDs, path order, or mastery conclusions.
- Do not make the feed a generic entertainment feed.
- Do not let the learning shadow publish without explicit user approval.
- Do not remove the direct daily mission entry just because the feed is the more distinctive surface.

## Next Safe Implementation Slice

1. Expand planner/research eval beyond the current structural gate with real LLM planner samples, semantic quality rubrics, and factuality review.
2. Improve source retrieval beyond search-result summaries with stronger source-quality scoring.
3. Add release-grade desktop/laptop/mobile visual checks around at least one more non-technical scripted E2E scenario.
4. Improve comment ranking beyond the current deterministic `热度` / `新回复` / `相关` modes with timestamp-aware hot/new scoring and learner-specific relevance after the reply loop remains stable across arbitrary topics.
5. Add a Boss-check milestone only after the current one-day loop is stable across arbitrary topics.

This order improves product depth while preserving the current architecture boundary.
